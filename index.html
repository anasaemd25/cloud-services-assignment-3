1. Why are so many companies using cloud-based email and calendar services?

In the past, running communications trough email in businesses meant buying physical hardware for a server, installing software like Microsoft Exchange or Thunderbird and keeping dedicated IT personal around it just to manage mailboxes. Today almost every company has shifted to cloud-based email and calendar platforms like Microsoft 365 or Google.

The main reason for this migration is that self-hosting email has become a problem for IT teams. An email server needs to stay active 24/7 with 0 downtime, because even a short outage can completely stop business operations.

On top of that, handling email security, manually managing spam filters, and complex domain authentication rules so the emails don't end up in a massive resource sink. So large cloud providers have become dominant on global email delivery, making it nearly impossible for small or medium self-hosted servers to be trusted and reliable.

Switching to cloud services also makes employee collaboration easier across different devices. Workers can schedule meetings, view shared team availability and join online calls from anywhere without dealing with VPNs.

By adopting this SaaS model, companies convert maintenance problems and severe security risks into a stable and predictable monthly subscription where the cloud provider manages the server, software updates, and backups.

2. Why do many IoT devices use Google's 8.8.8.8 or other public DNS resolvers?

IoT hardware like smart TV, home security cameras, IPTV devices usually ignore local router settings and public DNS resolvers like Google (8.8.8.8) or Cloudflare (1.1.1.1) directly instead of using the local ISP's DNS.

The main reason manufacturers hardcode these public DNS servers into their device is to make sure global reliability and consistency. Home routers and local ISP DNS servers can often be slow, misconfigured, or sometimes offline.

If a smart TV relied exclusively on a home router DNS, the TV might fail to reach its streaming servers, making the user thibk is because of the manufacturer for making a broken device. Hardcoding a universally reliable resolver like 8.8.8.8 ensures the device can translate domain names to IP addresses anywhere in the world without depending on local network stability.

Another factor could be bypassing local network blocks or DNS hijacking. Some home routers or local ISPs block or modify DNS requests for some regions, ad-filtering, or security reasons.

By communicating directly with public resolvers, IoT devices make sure an unblocked connection back to their manufacturer's infrastructure, allowing them to download system updates, report device health, and stream media smoothly regardless of the local network environment.

3. When should you maintain your own web server and when should you use SaaS, PaaS, or IaaS?

Choosing between running your own physical web server or relying on cloud service models like IaaS, PaaS, SaaS comes down to finding the right balance between control, operational effort, and total cost.

Maintaining a self hosted physical web server only makes sense in very specific scenarios, for example when an organization/bussines faces strict legal law requirements, already owns server hardware, or requires full low-level access to customized physical hardware and OS kernels.

However, this choice comes with high upfront costs, such as buying servers, a lot of storage, cooling systems, as well as constant need to mainten stuff like hardware repair, power, physical security, and manual scaling.

For almost every other modern web service, cloud models offer a much smarter alternative:

Infrastructure as a Service (IaaS)

I would choose IaaS, such as AWS EC2, Azure VMs, or CSC cPouta, when I need full virtual machine control to run custom applications but I don't want the hassle of managing physical hardware. I handle the OS updates and application setup while the cloud vendor maintains the host hardware.

Platform as a Service (PaaS)

PaaS, such as CSC Rahti or Render would be my choice when the goal is purely writing code and shipping applications quickly as possible. PaaS automates server configuration, OS security patches, container builds, and scaling. It is ideal for modern microservices and web apps where development speed matters way more than tuning OS settings.

Software as a Service (SaaS)

SaaS, such as Shopify or Gmail, is best when you just need a fully functional, ready to use platform and have 0 interest in managing application code, databases, or infrastructure.

4. Amazon S3 data leak incidents

Amazon S3 object storage is pretty secure by default, but human error and bad permission configuration by system administrators have caused gigant public data leaks over the years.

Three well-known S3 bucket leak incidents:

US Department of Defense (CENTCOM) Leak 2017

The defense contractor Booz Allen Hamilton accidentally left an AWS S3 bucket configured for public access without password protection. The bucket had sensitive military intelligence data including battlefield chat, logs and credentials belonging to military staff. The root cause was bassicly a misconfiguration, setting bucket access permissions to "Public" instead of restricting access to only for authenticated users.

Verizon Customer Data Leak 2017

A 3rd party vendor handling customer service analytics for Verizon left an unsecured S3 bucket exposed to the open web. The leak exposed personal information, account PINs and contact details for over 14 million customer. What went wrong was poor Identity and Access Management and weak third-party permissions monitoring.

Twilio / Accentuate S3 Bucket Hijacking

Black hat attackers targeted exposed or misconfigured S3 buckets used by software supply chains. They identified abandoned S3 bucket names referenced in web code, hackers re-created those bucket names under their own AWS accounts, then thhey could serve compromised JavaScript files directly to active web applications.

Automated Search Engines and Attack Tools

Security researchers and malicious actors use automated tools to discover publicly exposed storage buckets. Some examples include:

  • Grayhat Warfare: A searchable web database that indexes millions of open publicly exposed S3 buckets and their files
  • AWSBucketDump: A command line Python script that uses custom wordlists to brute force S3 bucket names and download exposed public files automatically.
  • S3Scanner: This scanner is a tool designed to automatically check lists of S3 URLs for weak read/ write permissions and dump accessible bucket data.

Practical Task Documentation

1. Source Code and Dockerfile Configuration

For this assignment, I created a public GitHub repository named cloud-services-assignment-3 to store my application code (index.html) and build instructions (Dockerfile). Instead of configuring a server manually, a Dockerfile defines the container environment that CSC Rahti builds automatically from Git. Following the same security requirement as in Week 2, CSC Rahti executes containers using an unprivileged user ID rather than root. Standard web servers try to bind to privileged port 80 by default, which causes a "Permission denied" on OpenShift. To avoid this, I used the nginxinc/nginx-unprivileged:alpine base image which listens on port 8080 by default.

2. Container Deployment on CSC Rahti

Deploying to CSC Rahti shows the primary advantage of a PaaS. Instead of building Docker images locally, I provided Rahti with the link to my public GitHub repository and Rahti automaticly builds it, creates the deployment, and scheduled Pods across the cluster. If a running Pod crashes or gets deleted, the underlying Kubernetes orchestrator automatically detects the problem and makes a replacement Pod to guarantee service availability without manual intervention.

3. CSC Allas Object Storage Setup

The primary objective of this exercise is implementing a hybrid PaaS and Object Storage architecture. Instead of adding the screenshots directly inside the web container, which could bloats the container image size and increases PaaS resource, screenshots/files are stored externally. I navigated to the MyCSC portal and verified that the Allas service was enabled under my active project. I then initialized a new object storage bucket named Weekly-assignment-3 to serve media separately over HTTP/HTTPS.

4. Public Object Storage and Asset Linking

In object storage systems like CSC Allas, data is stored as flat objects inside buckets rather than inside file directories. To serve these images to end users when they are browsing my Rahti website, I uploaded all screenshots PNG files to the Weekly-assignment-3 bucket and set the access policy to public. Each image have a unique public URL. In index.html, I added these public links directly inside the img tags. When somebody visits the website hosted on Rahti, their browser downloads the text from the PaaS container while fetching image files directly from Allas, completely offloading the media traffic from the container process.
